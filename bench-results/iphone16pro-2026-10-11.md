## Takeaways

- **No dropped frame at 120 Hz.** StreamText's worst frame is 8 ms (one 120 Hz frame) in every cell but 20 × 600 B.
  The old text view path drops about 7 frames for 50 KB (57 ms) and about 10 for 20 × 5 KB (89 ms); `<Text>` drops
  up to 40 (347 ms) for 20 × 5 KB.
- **50 KB shows in 34 ms**, as on the simulator; `<Text>` and the old path take 58–59 ms.
- **CoreText lays out 50 KB in 10 ms, TextKit in 18.5 ms** on the device (11.3 / 23.8 on the simulator): CoreText stays
  about twice as fast on hardware.
- **Weak spot: 20 × 600 B** has a 22 ms worst frame (2–3 frames) on the device, 17 on the simulator.
- **JS time at commit** is StreamText's cost: 30 ms for 50 KB, 50 ms for 20 × 5 KB (the layout is prepared in the
  commit; see HANDOFF C.21). The old path costs 2–5 ms of JS but drops frames instead.

## Why CoreText takes 10 ms in the probe and ~30 ms at mount

The probe lays the text out last, after a dozen other layouts have run the CPU up to speed; a mount
starts after an idle pause. The same 50 KB CoreText layout on the prepare queue's QoS (`userInitiated`),
medians of 5 ([cold start](probe-iphone16pro-coldstart-2026-10-11T20-37-18-201Z.json),
[QoS](probe-iphone16pro-qos-2026-10-11T20-32-26-915Z.json)):

| when | 50 KB | mixed 50 KB | 5 KB |
|---|---|---|---|
| after a 0.5 s pause, a text never laid out | **32 ms** | 17 ms | 8.3 ms |
| right after, the same text | 21 ms | 13 ms | 4.9 ms |
| right after, another new text | 16 ms | 12.7 ms | 4.2 ms |
| at the end of the probe | 10 ms | 6.9 ms | 1.0 ms |

It falls with time, not with the text being known: the CPU ramping up after idle. So ~30 ms is the
honest cost of mounting 50 KB when the app was idle (opening a chat), and 10 ms is a warm CPU. QoS is
not it: `userInitiated` and `userInteractive` match the main thread (9.6 ms), `utility` takes 23 ms.

## Text selection on the canvas (device)

Peek, mixed 5 KB text on a CoreText canvas: a long press selects a word with both handles and the menu
(Copy, Select All, Writing Tools, Look Up); dragging a handle extends the selection, keeping an emoji whole; copying and
tapping outside clear it. **The keyboard never shows**, which the simulator (hardware keyboard) could not prove.

## Running the benchmarks on a device

The example reaches the stream server at `localhost`, which on a phone is the phone itself. For a device run:

1. Temporarily set `SERVER` in `example/src/bench/config.ts` to the Mac's LAN address (`ipconfig getifaddr en0`).
   Don't commit it.
2. Start the server on the LAN: `HOST=0.0.0.0 node server/stream-server.mjs`. Stop it after the run.
3. Build and install Release for the device with a signing team, e.g.
   `xcodebuild -workspace TextStreamExample.xcworkspace -scheme TextStreamExample -configuration Release
   -destination id=<udid> -derivedDataPath build-device DEVELOPMENT_TEAM=<team> CODE_SIGN_STYLE=Automatic
   -allowProvisioningUpdates build`, then `xcrun devicectl device install app --device <udid>
   build-device/Build/Products/Release-iphoneos/TextStreamExample.app`.
4. On the first request iOS asks for local network access: allow it, then start the run again.
5. Keep Auto-Lock off for the full mount run (about 25 minutes). Device and Mac clocks differ, so latencies computed
   against the server's send log are not exact on a device; mount and probe only take their samples from the server.
